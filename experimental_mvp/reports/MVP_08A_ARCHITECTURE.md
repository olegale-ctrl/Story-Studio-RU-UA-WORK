## Data layout and transaction boundary

`<library>/catalog.sqlite3`; `objects/<sha256>.<validated extension>`; `staging/<import uuid>.<extension>`; `thumbnails/<derived key>.png`. Library is an explicitly selected trusted-user local directory, private mode requested for newly created directories on POSIX; not a qualified ACL security boundary. No media binaries are stored in Git.

Content identity is SHA256; Asset identity is independent UUID. The `assets` table stores current metadata revision plus operational integrity/lifecycle. `revisions` stores immutable JSON metadata snapshots. Multiple records may share one binary object while retaining different provenance and rights. Metadata revisions never overwrite original bytes. `imports` is a durable intent/status journal; `links` observes attachment history; `derivatives` stores thumbnail descriptors. Schema DDL creation is itself one transaction, so interrupted initialization cannot leave half a version0 catalog. SQLite `BEGIN IMMEDIATE` serializes writers/recovery, including staging and validation, with90s lock timeout and FULL synchronous writes. This favors correctness over write throughput; concurrent independent imports were tested.

Import: validate metadata/path/type/size → durable PENDING intent → acquire writer transaction → open regular source without following final symlink where supported, compare identity → stream into staging/hash/fsync → compare source handle/path identities → probe/decode staging and rehash → find shared content object → atomic same-directory-filesystem publication → verify object → insert record/revision and COMMITTED intent atomically in SQLite. Successful duplicate creates a new AssetRecord, not a new rights claim or binary copy. Known corrupted object is never overwritten by re-import.

Filesystem and SQLite are **not a distributed atomic transaction**. If process exits after file publication but before DB commit, file is retained, no ACTIVE record exists, and PENDING intent survives. Recovery marks incomplete imports ABORTED, cleans only reserved UUID staging names, verifies catalogued objects and never auto-activates an orphan. A later explicit import can reuse verified retained bytes. A crash after SQLite commit may leave staging cleanup pending; recovery cleans it. Originals and published objects are never garbage-collected in MVP-08A. Process-crash guarantees cover preserved source files and committed records. Pending metadata is not a durable draft: an aborted import may require re-entering provenance/rights on explicit retry; recovery does not claim to resume it. Guarantees do not include disk/controller failure or power-loss durability of directory entries.

## VideoAnchor / Timeline

The dataclass still has exactly17 fields. Optional `asset_library_binding` is an experimental dictionary extension like existing asset_sha256/provenance; it adds no normative PG fields. Attach resolves exact AssetRecord revision and current integrity/rights/lifecycle, compares all anchor editing fields with `anchor_token`, then rechecks immediately before association. A source/rights/metadata revision change blocks use; no substitution to latest metadata. Existing material requires explicit replacement. A binding saves prior material fields/binding for detach; old bytes and historical links remain. Deleted/edited target gives STALE_TARGET.

Project JSON is authoritative for scene membership. SQLite links are attachment observations, including historical/detached links; search does not claim to have scanned every saved project or to be a live referential index after Undo/duplicate/delete. The database event can persist if applying/saving the project fails; it never automatically reattaches or rewrites a project. This explicit two-resource boundary prevents a misleading atomic-save guarantee. No object deletion is implemented, so stale link observations cannot cause data loss.

Storyboard validate/render/video_spec resolve library bindings before preview/use and recheck hash; render still copies inputs and checks copied hashes. Legacy unbound assets retain their existing path behavior. Timeline.asset_change commits a background-validated candidate only against exact project snapshot and uses existing Undo/Redo stacks; it clears approved. UI edits loaded Timeline snapshot when available; otherwise applies to current project. User must explicitly apply/save Timeline afterward. Old bindings restored by Undo are resolved again: revocation/retirement/corruption blocks playback rather than silently replacing material.

## GUI and local previews

Asset Library tab: open/search, import, stable pages50, technical/provenance/rights details, local thumbnail, full metadata JSON review, anchor selection, attach/detach, retire and verify/recover. Work uses daemon threads with plain-data closures and queue results; network absent. Tk updates and CAS commits are GUI-thread only. On close Tcl image/variable resources are released on GUI thread; before starting a worker pending Tk garbage is collected on GUI thread. This fixes a reproduced cross-thread Tcl finalization crash. A finishing import after panel closure may remain safely catalogued but cannot mutate a closed project; no instant decoder cancellation claim. Tool commands have20s timeout, SQLite lock wait up to90s. Multiple major UI threads/other application code are not globally sandboxed.

Thumbnail is a separate DERIVED descriptor keyed by asset/revision/content/parameters/toolversion; first frame, fixed scale/max512, no original mutation. Descriptor includes source hash, own SHA, parent revision, parameters, tool version; cached corrupt thumbnail regenerates, original metadata revision does not change. With fixed bytes/FFmpeg build/parameters repeat output hash was verified. Not a cross-version bit-exact guarantee or artistic/rights approval. Explicitly registered preview files can be imported with source_type DERIVED and input references. No automatic media generation or dispatcher is implemented.
