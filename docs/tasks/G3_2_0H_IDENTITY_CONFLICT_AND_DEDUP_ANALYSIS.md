# Identity, integrity conflict and dedup — seven separate families

**DOCS_ONLY. F-D01 and every H-D decision: PROPOSED — NOT APPROVED.**

## Key ≠ expected metadata ≠ observed bytes

[PROPOSED] Keep three records conceptually separate: (1) stable registry identity K under a selected namespace/family, (2) expected integrity/descriptor constraints I for K, (3) actual independently supplied/observed byte sequence B and target header. These are analysis symbols, not new wire schema/API fields. Source [C P2 reference/schema](G3_2_0C_P2_REFERENCE_AND_SCHEMA.md) §1 registry paragraph; [A schema/reference inventory](G3_2_0A_SCHEMA_AND_REFERENCE_MATRIX.md) reference records; [F pure choices](G3_2_0F_PURE_CONTRACT_DECISION_OPTIONS.md) CM-071.


[OPEN_CONTRACT_DETAIL] Defining K=(object_id,hash,length) alone can turn inconsistent hash/length claims for one supposedly immutable object into different successful registry entries. Candidate raw key excludes metadata: namespace+raw-family+object_id. That choice is recommended for analysis, not approved. When the object format is unversioned, no revision may be invented to legitimise changed bytes. Need an explicit new-ID/version policy if material changes.

[OPEN_CONTRACT_DETAIL] PG ObjectRef is different: approved PG-C14N-1 permits multiple wire spellings of the same parsed value/binding. Raw-byte difference alone need not mean canonical semantic difference. Strict raw distribution policy may be a separate future constraint, never a changed hash algorithm. Keep raw artifact identity and PG canonical correspondence distinct; see H-C027/H-D03.
