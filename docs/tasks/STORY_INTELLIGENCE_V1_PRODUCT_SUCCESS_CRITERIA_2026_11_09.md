# Продуктовый критерий успеха Story Intelligence V1

**Статус:** Рабочий документ для приёмки этапов
**Дата:** 2026-11-09
**Основание:** Утверждённая архитектура Story Intelligence, SI-D01–SI-D10, целевой пользовательский сценарий владельца

---

## 1. Назначение документа

Этот документ фиксирует, **что считается успехом** Story Intelligence V1 с точки зрения продукта, а не только с точки зрения технических контрактов.

Он не отменяет SI-D01–SI-D10, provenance, blocking-риски и редакционные ограничения.

Он дополняет их обязательным требованием: каждый крупный этап должен приближать систему к реальной пользе для редактора.

## 2. Главный вопрос, на который должна отвечать система

Редактор должен получить быстрый и понятный ответ на три связанных вопроса:

1. Стоит ли снимать видео на эту тему для нашей аудитории и канала?
2. Почему (какие сильные стороны и какие риски)?
3. Как лучше подать тему и что необходимо подготовить перед производством?

Если система не помогает ответить на эти вопросы быстрее и надёжнее, чем работа «вручную», этап не считается продуктово успешным — даже при идеальном выполнении всех технических проверок.

## 3. Целевой пользовательский сценарий (Definition of Success)

**Вход (минимум):**

- Тема
- Целевая аудитория (или гипотеза аудитории)
- Язык
- Формат / ориентировочная длительность

**Ожидаемый результат:**

**Краткая карточка решения**

- Почему тема перспективна (или почему нет)
- Основные риски (особенно blocking)
- 2–3 варианта подачи
- Рекомендуемый следующий шаг

**Расширенный Production Brief**

- Структура видео
- Проверяемые тезисы и статус их подтверждения
- Источники и ограничения
- План визуалов (обязательное / желательное / заменяемое)
- Что должен сделать человек перед запуском производства

Рекомендация системы **не заменяет** редакционное утверждение.

## 4. Обязательные свойства результата

Результат считается приемлемым только если он одновременно:

| Свойство | Требование |
| --- | --- |
| Понятность | Редактор понимает вывод без знания внутренних типов (SIRef, RunRecord, provenance и т.д.) |
| Честность | Неподтверждённые тезисы не выдаются за факты. Неопределённость явно обозначена |
| Действенность | Из карточки ясно, что делать дальше (продолжить исследование / выбрать подачу / отклонить / запросить материалы) |
| Производственная реалистичность | Учтены права, доступность визуалов и реальные ограничения ресурсов |
| Сохранность границ | Creative-предложения не искажают исследовательские факты и не обходят blocking-риски |

## 5. Минимальный набор проверяемых сценариев

Для сквозной продуктовой приёмки (начиная с SI-E04) обязательно прогоняются минимум три разных случая:

1. **Историко-научная тема с неопределённостью**
   Пример: «Почему исчезли древние цивилизации?»
   Проверяем: корректную работу с неполными данными, альтернативные подачи, запрет выдавать гипотезы за факты.
2. **Простая тема с ограниченными ресурсами**
   Проверяем: честную оценку реализуемости и предложение упрощённых визуальных решений.
3. **Тема с проблемами прав на визуальные материалы**
   Проверяем: выявление blocking/non-blocking рисков и предложение безопасных альтернатив.

По каждому сценарию фиксируется:

- Сколько ручных действий потребовалось
- Насколько понятна рекомендация
- Можно ли на основе результата принять решение о следующем шаге

## 6. Критерии приёмки по этапам

| Этап | Технический результат | Дополнительный продуктовый критерий |
| --- | --- | --- |
| SI-E01 | Типы, codec, provenance, операции | Данные надёжны и непротиворечивы |
| SI-E02 | Ручной Discovery | Легко создать тему и увидеть возможные дубликаты |
| SI-E03 | Evaluation | Понятно, почему тема получила оценку и какие риски её блокируют |
| SI-E04 | Creative + Production Brief | Можно пройти полный путь от темы до пригодного для обсуждения Brief |
| SI-E05 | Workspace + ReviewPacket | Можно безопасно продолжить работу после перезапуска |

**Особое значение имеет SI-E04.**

Он является первой полноценной продуктовой приёмкой, а не только проверкой очередных классов.

## 7. Что не является критерием успеха V1

- Количество реализованных типов и сущностей
- Полнота покрытия всех возможных краевых случаев
- Наличие LLM или онлайн-поиска
- «Красивость» внутренних структур данных
- Высокий балл по эвристической шкале сам по себе

Высокий балл — только сигнал соответствия выбранной модели оценки.

Реальная ценность подтверждается только тем, помогает ли результат редактору принять решение.

## 8. Рабочий принцип дальнейшей разработки

Каждый крупный этап после создания программного фундамента обязан приближать систему к работающему сценарию:

**идея → оценка → варианты подачи → Production Brief**

а не только увеличивать количество технических компонентов.

Этот принцип применяется при планировании и приёмке SI-E02 и последующих этапов.
