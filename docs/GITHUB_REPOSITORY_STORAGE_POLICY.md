# GitHub repository storage and collaboration policy — Story Studio RU/UA

**Дата принятия:** 2026-11-05
**Статус:** обязательная проектная политика для дальнейших заданий Codex, ревизий и ручных изменений.
**Репозиторий:** `olegale-ctrl/Story-Studio-RU-UA-WORK` (private).

## 1. Назначение и границы

GitHub/Git — система версий **кода, документации, конфигураций, лицензий и небольших тестовых фикстур**, а не универсальное файловое хранилище для готовых видеопроектов, больших медиа, моделей ИИ, личных данных или резервных копий. Отдельно учитывать рабочий каталог Git, историю всех веток, Git LFS, GitHub Releases и Actions artifacts: у них различаются квоты и жизненный цикл.

Этот документ **не изменяет** редакционные контракты E00/A1–A14/O1–O10, правила прав на материалы, архитектуру Story Intelligence или неутверждённый storage proposal E01.3.9.1. Запрещено хранить защищённые editorial head anchors, service keys, приватные approval/session evidence или production secrets в репозитории даже при его приватности.

## 2. Что можно коммитить

- Python и другие исходники, unit/integration tests, маленькие искусственные фикстуры, схемы JSON, локализации RU/UK, промпты, небольшие изображения/аудио **только при необходимости, с подтверждёнными правами и в пределах политики**.
- Архитектурные решения, задачи, отчёты, worklog, лицензии, SBOM, lockfiles, контрольные суммы и **метаданные** происхождения моделей/датасетов/медиа.
- Документацию по загрузке внешних зависимостей с точной версией, официальным источником, контрольной суммой и условиями лицензии; не подменять проверку прав автоматическим скачиванием.

## 3. Что нельзя помещать в обычный Git

- Готовые/промежуточные видео, TTS/ASR WAV/MP3, экспортные медиапакеты, массивные изображения, датасеты, скачанные веса моделей, локальные установщики и большие бинарные архивы.
- Секреты и ключи API, приватные сертификаты, токены, учётные данные, реальные персональные данные, сервисные HMAC/DPAPI ключи и защищённые production anchors/journals.
- Китайские Writing-DNA/корпуса со статусом REPLACE/BLOCKED; любой чужой контент без проверенных прав на размещение и распространение.
- Кэши, виртуальные окружения, результаты сборки, временные файлы, логи с секретами и автоматически созданные результаты рендера.

**Исключение:** минимальный бинарный тестовый образец может быть включён лишь после обоснования в задаче, проверки лицензии/конфиденциальности, размера и явного согласования владельца. Даже приватный репозиторий не даёт прав на распространение чужих материалов.

## 4. Лимиты и внутренние пороги

Официальные ограничения GitHub могут меняться. Проверять актуальные правила и доступные квоты аккаунта перед любым исключением или включением LFS. Не считать рекомендуемый размер репозитория гарантированной квотой.

| Объект | Правило проекта |
|---|---|
| Размер репозитория | Цель: обычный Git **до 1 ГиБ**, раннее предупреждение при 500 МиБ; если приближается к 1 ГиБ — аудит истории/бинарников и решение владельца. Внешние рекомендации GitHub по производительности проверяются отдельно. |
| Размер файла | **До 10 МиБ** — внутренний обычный максимум для нового файла; свыше 10 МиБ — отдельное согласование и предпочтение внешнего хранилища. GitHub предупреждает о файлах >50 МиБ и блокирует обычный Git-файл >100 МиБ. |
| Push | Не делать массовые push; документированный предел GitHub для одного push — **2 ГиБ**. Это не разрешение загружать 2 ГиБ медиа. |
| Git LFS | По умолчанию **не включать**. Только после явного решения владельца, проверки текущих лимитов хранилища, трафика, стоимости, доступа и правил удаления. |
| GitHub Actions artifacts / Releases | Не использовать как постоянное бесплатное хранилище. Учитывать отдельные ограничения, retention и стоимость. |

Источники для периодической сверки:
- https://docs.github.com/en/repositories/creating-and-managing-repositories/repository-limits
- https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github
- https://docs.github.com/en/billing/concepts/product-billing/git-lfs
- https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-storage-and-bandwidth-usage

## 5. Места хранения больших артефактов

- Модели/веса: локальный каталог `models/` вне Git; скачать только из подтверждённого источника, сверить hash и лицензию. Для разработки с Silero CC BY-NC — только dev/test до повторного аудита перед коммерческим использованием.
- Видео, звук, кадры, рендеры и рабочие медиа: локальные `media/`, `outputs/`, `renders/`, `cache/` либо специально выбранное внешнее хранилище. Публикация в облако только с согласия владельца, после проверки конфиденциальности и прав.
- Backup: независимые проверяемые резервные копии в управляемом хранилище; **не** Git history, не GitHub LFS и не ZIP внутри репозитория. Отдельно проверять восстановление и сохранение отозванных approvals; никакого автоматического восстановления доверия из backup.
- Для воспроизводимости в Git хранить **manifest** (название, версия, источник, SHA-256, статус прав, инструкция загрузки), а не тяжёлый объект.

## 6. Перед каждым commit/push

1. Проверить текущую ветку, базовый SHA, `git status`, `git diff --stat`, список новых/изменённых файлов и их размеры.
2. Проверить `git diff --check`, отсутствие секретов, PII, запрещённых лицензией активов, больших медиа и случайных бинарников. Не заявлять о запуске проверок, если они не выполнялись.
3. Проверить, что `.gitignore` защищает типичные generated files. **Важно:** `.gitignore` не удаляет уже отслеживаемые файлы и не заменяет сканирование секретов.
4. Не добавлять крупные/запрещённые файлы через `git add -f`, переименование расширения, архивирование или LFS в обход правил.
5. Сверить изменённые документы и зависимости с точными SHA/версиями. В отчёте Codex перечислить файлы, размеры при необходимости, проверки и новый commit SHA.
6. Работать только в явно согласованной feature/docs ветке; **не менять `main`, не создавать PR, не выполнять merge, release или публикацию** без отдельного разрешения владельца. Новые ветки создавать от указанного полного SHA.
7. Принятые архитектурные решения фиксировать отдельными docs-only коммитами; при конфликте с утверждёнными контрактами не исправлять код самовольно, а вынести решение владельцу.

## 7. История Git и инциденты

Удаление файла новым коммитом **не удаляет его из истории Git**. При случайном попадании секрета: немедленно отозвать/ротировать секрет, остановить распространение и согласовать безопасную очистку истории с владельцем; `git filter-repo`/force-push не выполнять автоматически. При попадании большого бинарника сначала оценить, в каких ветках и коммитах он находится; не переписывать историю без явного решения и плана для всех копий.

Для больших артефактов предпочтительны внешнее хранение с checksum/manifest и повторяемая сборка. Данные не считаются надёжно сохранёнными только потому, что они были загружены в GitHub.

## 8. Контроль

Проверять размер репозитория и состав больших объектов периодически и перед крупными импортами. GitHub API `size` — приблизительный показатель в КБ, **не** точный размер полного локального clone или всех LFS объектов. При превышении внутреннего порога готовить отдельный отчёт и план, а не автоматически удалять файлы.

Политика применяется ко всем будущим заданиям Codex и ручным изменениям. Изменения самой политики — отдельное документированное решение в новой ветке.
